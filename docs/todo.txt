# THE LOOP — every TODO item follows these six steps

  1 INSPECT       read the files the item names before touching anything, and
                  confirm its claims still hold at current HEAD
  2 IMPLEMENT     only that item's change; no drive-by edits, no bundling
  3 TEST          the item's own verification, plus always:
                    npm run typecheck                (repo root)
                    cd server && npm run typecheck
                    npm run build                    (repo root)
  4 INSPECT DIFF  git status --short
                  git diff — read every hunk; nothing unrelated may be in it
  5 COMMIT        git add only that item's files, one item per commit, with the
                  subject the item gives and a prose body saying why
  6 VERIFY COMMIT git log -1 --stat, then git status --short must come back clean

Each item below repeats these six with its own specifics. Do not modify the
completed voting work in section B unless an actual bug is found; if one is,
fix it as its own item with its own commit.

  C2  Automatic phase progression, admin override kept                   [DONE]
      LANDED: there is no scheduler process, so reading the open round is what makes
      time pass. findCurrent applies whatever the deadlines are owed before it
      returns, which puts one phase in front of every consumer at once — the vote
      endpoints, the submission endpoints, the admin routes and the client all call
      it, so none of them can act on a round the clock has already moved past.
      A round left alone can be owed more than one step, so they are applied in order
      in one pass: submission -> voting, then the ballot close, then challenge ->
      ended. The pass always stops at the approval; no deadline stands in for an
      administrator confirming a winner.
      Races: the phase is in the UPDATE's WHERE clause, so the first concurrent read
      wins and later ones match nothing, and the ballot close is already refused once
      winner_status leaves 'none'. Clocks: the comparison uses the database's now(),
      so an app clock running fast leaves the move to the next read rather than
      advancing early. The automatic path also asks canTransition, so the clock can
      never do a move the admin endpoint is refused.
      A round with nothing approved is left alone on purpose — 'no-entries' keeps the
      ballot open rather than closing it into a state only a result correction could
      undo, and an administrator decides.
      NOT DONE, and it is not in this item's WHAT: my_plan.txt:773 also wants the UI
      to say the round is automated. The countdowns are now truthful, which is most of
      it; explicit "advances automatically" copy is a suggestion for the owner, not
      something this item claimed.
      STILL TO VERIFY, in the final pass: the deadline behaviour needs a deadline that
      has actually passed. Nothing is due on the local instance (voting ends
      2026-09-13), so the tick was confirmed only as a no-op. The check is in this
      item's VERIFY and needs an admin session to move a deadline via PATCH
      /api/admin/round/phase with endsAt, not a hand-written UPDATE.
      DECIDED  Submission -> Voting -> Challenge -> Archive advances automatically
               on the configured phase end times, with one exception: Voting ->
               Challenge requires winner approval. Administrators may also advance
               by hand when appropriate. Backwards transitions are refused (C3).
               The next round does NOT open automatically: only an admin creates
               it, and only after the previous round is archived.
      WHAT   An advance-if-due check that runs server-side before the open round is
             served — in findCurrent, or in a small tick beside it — comparing the
             current phase's *_ends_at to now() and applying exactly the same
             transition the admin endpoint applies, through the same repo function
             so the two paths cannot diverge.

             THE FULL CHAIN, and what is automatic in each step:

               submission --(submission_ends_at passes)--> voting        AUTOMATIC
               voting     --(voting_ends_at passes)------> ballot closes AUTOMATIC
                                                           winner_status becomes
                                                           'pending' or 'tiebreak';
                                                           phase stays 'voting'
               voting     --(admin approves the winner)--> challenge     ADMIN ONLY
               challenge  --(challenge_ends_at passes)---> ended         AUTOMATIC

               (next round)                                              ADMIN ONLY

             Consequence to design for: src/lib/round.ts toCurrentRound maps an

# THE WINNER STATE MACHINE  (D1 + B10 + C2, in one place)

  rounds gains winner_status, one of:

    none        the round has not finished voting
    pending     voting closed, one clear top entry, awaiting admin approval
    tiebreak    voting closed, two or more level at the top, awaiting an admin
                choosing between them
    official    an admin approved it; permanent

  voting_ends_at passes (C2), or an admin ends voting by hand
        │
        ├── exactly one highest count ──> winner_status = 'pending'
        │                                 winning_submission_id = that entry
        │                                 winner_vote_count, total_votes frozen
        │                                 phase stays 'voting'
        │                                 admin approves ──> 'official', phase 'challenge'
        │
        └── two or more tied ──────────> winner_status = 'tiebreak'
                                          tied entries recorded, no winner set
                                          phase stays 'voting'
                                          admin selects one ──> 'official', phase 'challenge'

  A VALIDLY CAST VOTE IS PERMANENT. Blocking a voter later (C5) only stops them
  voting again; it never removes a vote already cast. Rejecting a submission after
  votes were cast for it does not retroactively delete or discount those votes
  either. The only way a recorded result changes is an administrator performing an
  explicit, separate result correction (D4) — never as a side effect of a block or
  a review. So "highest valid vote count" means: every vote that was validly cast
  while the ballot was open, counted as cast.

  THE BALLOT CLOSES ON winner_status, NOT ON THE PHASE. The vote endpoints
  currently gate on phase === 'voting' alone; they must also require
  winner_status === 'none', or votes would keep landing while a winner sat pending
  and the frozen counts would stop matching the table.
